# UP Labs — ข้อมูลสุขภาพลูกค้า

ต่อกับ UP Labs (`upwellness-ops.vercel.app`) ผ่าน REST API เพื่ออ่านและอัปเดตข้อมูลสุขภาพลูกค้าของ UP Wellness

## ตั้งค่าครั้งเดียว

ต้องมี token ใน environment:

```bash
export UPLAB_TOKEN="uplab_live_xxxxxxxx_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
```

ขอ token ได้ที่ `https://upwellness-ops.vercel.app/v2/admin/api-tokens` (ต้องเป็นแอดมิน)
ถ้ายังไม่ได้ตั้ง ให้บอกผู้ใช้ว่าต้องตั้งตัวแปรนี้ก่อน **อย่าถามหา token มาพิมพ์ในแชท**

## วิธีใช้

สคริปต์ `scripts/uplabs` ห่อทุก endpoint ไว้แล้ว — เรียกผ่านมันเสมอ อย่าเขียน curl เอง

```bash
scripts/uplabs whoami                      # token นี้ทำอะไรได้ เห็นลูกค้ากี่คน
scripts/uplabs find "ต้น"                  # หาลูกค้า → ได้ id
scripts/uplabs profile <id>                # โปรไฟล์ + มีข้อมูลอะไรบ้าง
scripts/uplabs compare <id> 3              # ★ ตารางเทียบผลแล็บ 3 รอบ + delta
scripts/uplabs overview <id>               # ★ ภาพรวมทุกด้าน + ค่าผิดปกติ + ที่ยังไม่เคยตรวจ
scripts/uplabs metric <id> hba1c           # ค่าตัวเดียวทุกครั้ง (ทำกราฟ)
scripts/uplabs bca <id>                    # องค์ประกอบร่างกาย
scripts/uplabs supplements <id>            # อาหารเสริม + ความปลอดภัยคู่ยา
scripts/uplabs notes <id>                  # โน้ตโค้ช
scripts/uplabs note <id> "ข้อความ"          # เพิ่มโน้ต
scripts/uplabs cgm-import <id> ottai.xlsx  # ★ นำเข้าไฟล์ Ottai (ซ้ำได้ ไม่เขียนทับ)
scripts/uplabs cgm-metrics <id> 14         # ★ TIR/TBR/CV/GMI 14 วัน — ดู reliable ก่อน
scripts/uplabs ask "คำสั่งภาษาไทย" [id]     # ถามแบบไม่ต้องเลือก endpoint
```

## ขั้นตอนที่ถูกต้อง

1. **หา id ก่อนเสมอ** — `find` ก่อน แล้วค่อยเรียกอย่างอื่น
2. **เจอหลายคน = หยุดถาม** ห้ามเลือกให้เอง (ดูข้อควรระวังด้านล่าง)
3. เรียก endpoint ที่ตรงกับคำถาม — เทียบย้อนหลังใช้ `compare` · ถามภาพรวมใช้ `overview`
4. อ่าน `caveats` / `never_tested` ก่อนสรุป
5. ตอบเป็นภาษาคน ไม่ใช่ JSON

## ⛔ ข้อควรระวัง — ผิดแล้วเสียหายจริง

**ชื่อซ้ำ = ห้ามเดา**
ในระบบมีลูกค้าที่ชื่อคล้ายกันจริง (ต่างกันแค่คำนำหน้าหรือปีเกิด) · ถ้า `find` คืนมามากกว่า 1 คน
**ให้แสดงรายชื่อพร้อมอายุ แล้วถามผู้ใช้ว่าหมายถึงใคร** — ตอบผิดคนคือส่งประวัติสุขภาพผิดคน
API เองก็จะคืน `needs_disambiguation` ถ้าคุณส่งชื่อกำกวมไป นั่นคือฟีเจอร์ ไม่ใช่บั๊ก

**`null` ไม่ใช่ศูนย์**
ในตารางเทียบ `null` แปลว่า **รอบนั้นไม่ได้ตรวจตัวนั้น** · ห้ามอ่านเป็น 0 ห้ามยกค่ารอบก่อนมาเติมเอง

**"ไม่มีข้อมูล" ไม่เท่ากับ "ปกติ"**
`overview` แยก `abnormal` (ตรวจแล้วผิด) ออกจาก `never_tested` (ไม่เคยตรวจ) ให้แล้ว — ต้องรายงานทั้งสองอย่าง
การสรุปว่า "สุขภาพดี" ทั้งที่ครึ่งหนึ่งไม่เคยตรวจ คือการให้ความมั่นใจที่ไม่มีหลักฐานรองรับ

**ไม่วินิจฉัย**
wellness ≠ diagnosis · ค่าผิดปกติ → แนะนำพบแพทย์ · อาหารเสริม → ต้องผ่านเภสัชกรและแพทย์
ห้ามใช้คำว่า "รักษา" "หาย" "100%" · ใช้ "สนับสนุน" "ช่วยให้" "สัมพันธ์กับ" แทน

**ตัวเลขทุกตัวมาจาก API เท่านั้น**
ถ้ายังไม่ได้เรียก ก็ยังไม่มีตัวเลข · ห้ามประมาณ ห้ามเติมจากความจำ

## เมื่อ API ปฏิเสธ

| รหัส | หมายความว่า | ทำยังไง |
|---|---|---|
| `needs_disambiguation` | ชื่อตรงกับหลายคน | แสดง candidates ให้ผู้ใช้เลือก แล้วเรียกซ้ำด้วย id |
| `insufficient_scope` | token ไม่มีสิทธิ์นั้น | บอกผู้ใช้ว่าต้องขอ scope อะไร (อยู่ใน `required_scope`) |
| `customer_out_of_scope` | ลูกค้าไม่อยู่ในสายงานของเจ้าของ token | บอกตามตรง ไม่ต้องลองทางอื่น |
| `token_expired` · `token_revoked` | token ใช้ไม่ได้แล้ว | ให้ผู้ใช้สร้างใบใหม่ |
| `rate_limited` | เกิน 60 ครั้ง/นาที | รอสักครู่แล้วลองใหม่ |

## รูปแบบคำตอบที่ดี

- ขึ้นด้วย**คำตอบ** ไม่ใช่ JSON
- เทียบหลายรอบ → **ตาราง** เรียงเก่า→ใหม่ + ทิศทางที่เปลี่ยน
- ค่าผิดปกติ → บอก**เกณฑ์**ด้วย ไม่ใช่แค่บอกว่าผิด
- ปิดท้ายด้วย**สิ่งที่ยังไม่รู้** จาก `caveats` — ส่วนนี้มีค่าที่สุดและถูกมองข้ามบ่อยที่สุด
- ถ้าใบแล็บไม่ระบุบางอย่างที่มีผลต่อการตีความ (เช่น งดอาหารหรือไม่) → **พูดออกมา**

## อ่านค่าจากเอกสาร → เข้าคิวเสมอ ห้ามเขียนตรง

ถ้าผู้ใช้ส่งรูปหรือ PDF ใบแล็บมา ให้ยิงเข้า `POST /api/v1/customers/{id}/labs/submit` เท่านั้น
(ไม่ใช่ `/labs` ที่เขียนตรงเข้าประวัติ)

- ส่ง `raw_text` = สิ่งที่อ่านได้จากเอกสาร**แบบคำต่อคำ**มาด้วยเสมอ — คนตรวจใช้เทียบว่าอ่านตรงแถวไหม
- **ค่าไหนอ่านไม่ชัด ให้ข้ามไป ห้ามเดา** — ค่าที่เดามาแยกไม่ออกจากค่าที่อ่านถูก
- **สถานะ (ปกติ/สูง/ต่ำ) ใส่เฉพาะที่ใบพิมพ์ธงไว้** ห้ามอนุมานจากช่วงอ้างอิงเอง
- วันที่: ใบแล็บไทยพิมพ์ พ.ศ. — ต้องลบ 543 ก่อนส่ง
- หลังส่งเสร็จ บอกผู้ใช้ว่า **"เข้าคิวรอตรวจแล้ว ยังไม่ได้บันทึกลงประวัติ"** พร้อมลิงก์ `/v2/lab-inbox`

## ไฟล์ CGM (Ottai) → นำเข้าได้เลย ไม่ต้องเข้าคิว

ไฟล์ Ottai คือค่าจากเครื่อง ไม่ใช่ค่าที่ AI อ่านจากภาพ จึงเข้าประวัติตรงได้ (`cgm-import`)

- ไม่ต้องแยกคอลัมน์เอง เซิร์ฟเวอร์หา `Time`/`Glucose` ให้ · เวลาในไฟล์ถือเป็นเวลาไทย
- อัปโหลดไฟล์เดิมซ้ำได้ — ตอบกลับจะบอก `inserted` (ใหม่) กับ `skipped_existing` (มีแล้ว) แยกกัน
- ถ้าตอบ 400 พร้อม `existing_profiles` = ลูกค้ามีชื่อโปรไฟล์อยู่แล้ว **ไม่ต้องส่ง profile_name** ให้ยิงซ้ำโดยไม่ใส่
- อ่านตัวเลขด้วย `cgm-metrics` เสมอ **ห้ามดึงค่าดิบมาคำนวณเอง** · ถ้า `reliable: false` ให้พูดว่า "แนวโน้ม" ห้ามเทียบเป้า · อ่าน `caveats` ทุกครั้ง
- GMI ≠ HbA1c · เป้า TIR/TBR เป็นของคนเป็นเบาหวาน คนทั่วไปยังไม่มีเกณฑ์ทางการ
