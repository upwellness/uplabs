5 Data Flows หลัก

① ผลแล็บเข้าโปรไฟล์
ใบตรวจ (PDF/รูป) → อ่านค่าจริง → customer_records (1 ครั้งที่ตรวจ) → customer_lab_values (หลายค่า + status) → Customer 360 (Labs/Trends/Body Map) → Longevity Report
② เชื่อมนาฬิกา
โค้ชสร้าง invite → ลูกค้าเปิด /connect/[token] → OAuth → เก็บ token (เข้ารหัส) ใน pulse_connections → sync → pulse_readings/whoop_* → รายงาน → แชร์ /r/[token]
③ AI วิเคราะห์ (BYO key)
client อ่านคีย์จาก localStorage → POST /api/… พร้อม apiKey → lib เรียก Gemini → คืนผล → cache ลง DB · คีย์พัง → GeminiKeyErrorNotice ชวนไปขอคีย์ใหม่
④ Check FORM → ผู้มุ่งหวัง
โปรไฟล์+DISC → Gemini → แนวทางเข้าหา + คลิป STP → cache ใน checkform_records → prospect_list
⑤ สมาชิกใหม่ (MLM)
/v2/invite → user_invites → ลิงก์ /join/[token] → สมัคร → profiles.parent_id = ผู้เชิญ → เห็น downline แบบอ่านอย่างเดียว
⑥ LINE ประจำวัน
cron → /api/line/push-tomorrow → อ่าน plate_plan_config + supplement_schedule → ส่ง Flex เข้ากลุ่มใน line_bot_groups → log

6 Security & Access

ชั้นกลไก
AuthSupabase Auth (email+password) · session ผ่าน lib/auth/session.ts
Roleadmin / abo + user_app_grants รายแอป
ข้อมูลลูกค้าlib/customers/access.ts → canManageCustomer() = ด่านเดียว — เจ้าของ (coach_id) · ผู้ได้รับมอบหมาย · upline ของเจ้าของทุกระดับชั้น (อ่าน+เขียน · recursive ผ่าน RPC profile_descendant_ids) · ห้าม route เขียนเช็คสิทธิ์เอง
RLSเปิดบนตารางอ่อนไหว (cgm_readings, cgm_meals) · CGM ใช้ passcode + SECURITY DEFINER RPC
Service roleเฉพาะ lib/supabase/admin.ts ฝั่งเซิร์ฟเวอร์ · ห้ามหลุดไป client
ลิงก์สาธารณะtoken ใช้ครั้งเดียว/มีวันหมดอายุ (user_invites, pulse_invites, pulse_intakes)
ความลับAI key = BYO ในเบราว์เซอร์ · token อุปกรณ์เข้ารหัสก่อนเก็บ · repo public → ห้าม commit PII

7 🚀 ต่อยอดอะไรได้อีก

ข้อดีของการมีแกนกลาง: ทั้ง 13 ข้อนี้ ไม่ต้องเก็บข้อมูลใหม่เลย — เป็นการ “อ่านแกนเดิมในมุมใหม่” เรียงตาม ใช้ข้อมูลที่มีแล้ว → คุณค่าสูง → งานน้อย
#โอกาสใช้ข้อมูลที่มีแล้วต้องเพิ่มคุณค่า
1Longevity Report ปุ่มเดียวในแอปlabs + measurements + pulse + bio-agetemplate renderer ในระบบส่งมอบเร็วขึ้นมาก · เป็นบริการมาตรฐาน
2Health Age trend (PhenoAge หลายครั้ง)customer_lab_values ย้อนหลังกราฟ + เก็บผลคำนวณ“อายุสุขภาพลดลง” = แรงจูงใจแรงที่สุด
3Attention Queue — ใครต้องดูแลด่วนวันนี้status ทุก lab/BCA + วันที่ล่าสุดdashboard + ruleโค้ชเลิกเดาว่าจะโทรหาใคร
4Auto supplement stacklab values + supplement_safety + ยาrule engine + แคตตาล็อกคำแนะนำเฉพาะคน + ปลอดภัยกับยา
5อาหาร ↔ น้ำตาลnutriscan_scans + cgm_readingsjoin ตามเวลา“จานนี้ทำให้น้ำตาลคุณขึ้นเท่าไร” — ของจริงเฉพาะบุคคล
6นอน/HRV ↔ ค่าอักเสบwhoop_* + labs (hs-CRP)correlation viewเชื่อมไลฟ์สไตล์กับผลเลือด
7Program outcome analyticsmeasurements + labs ก่อน/หลังผูก “โปรแกรม” เป็น entityพิสูจน์ผลเป็นตัวเลข → ใช้ขาย/ปรับสูตร
8Adherence scoreLINE log + nutriscan + การเข้าใช้สูตรคะแนนรู้ว่าใครกำลังหลุด ก่อนหลุดจริง
9Household / family linkingที่อยู่ + ผู้แนะนำfield household_idดูแลทั้งบ้าน = LTV สูงขึ้น
10Lead → Customer ครบวงจรhealthcheck_leads · prospect_list · warm_leadsFK เข้า customers + funnel viewปิดช่องว่างที่ lead ยังไม่ต่อกับโปรไฟล์
11Coach / downline analyticsprofiles.parent_id + customers ต่อโค้ชdashboardเห็นว่าทีมใครโตจริง
12Benchmark ไม่ระบุตัวตนค่า lab/BCA ทั้งฐานaggregate + de-identify“คนวัยเดียวกันค่าเฉลี่ยเท่าไร”
13Clip/content แนะนำจากสุขภาพSTP matcher + โปรไฟล์สุขภาพขยาย matcher ให้รับ customerคอนเทนต์ตรงปัญหาเขาจริง

8 Conventions สำหรับคนที่มาต่อ

  1. ฟีเจอร์ใหม่ที่เกี่ยวกับคน → ต้องมี customer_id อย่าสร้างเกาะข้อมูลใหม่
  2. ตรรกะคลินิกอยู่ใน lib/ เท่านั้น (หน้าเว็บห้ามตัดสินเกณฑ์เอง)
  3. API route = ด่านตรวจสิทธิ์ + ที่เดียวที่คุยกับภายนอก
  4. เพิ่มแอป → ลงทะเบียนใน lib/apps-registry.ts + เพิ่มลิงก์ v2 ใน Shell.tsx
  5. แก้ฟีเจอร์ → อัปเดต PRD + ARCHITECTURE (md และ html) ในคอมมิตเดียวกัน
