## 1. Problem Statement

โค้ช UP Wellness มีข้อมูลลูกค้า 5 แหล่งอยู่ในระบบแล้ว (แล็บ · BCA · CGM · นาฬิกา · อาหาร) แต่ระบบ**ประเมินแยกกัน**: Health Score ดูแค่แล็บ+BCA · CGM มีตัวเลขสรุปแต่ไม่ถูกนำไปรวม · อาหารกับนาฬิกาอยู่คนละหน้า → โค้ชยังต้อง "รวมในหัว" แล้วเขียนแผนเอง ผลคือแผนไม่สม่ำเสมอระหว่างโค้ช พิสูจน์ที่มาไม่ได้ และลูกค้าเห็นผลก็ต่อเมื่อโค้ชว่างมาสรุปให้

ผลกระทบถ้าไม่แก้: คำโปรโมต "ออกแบบเฉพาะบุคคลบนข้อมูล" จะเป็นคำที่ทีมขายพูดแต่ระบบทำไม่ได้ · โค้ชใหม่ (downline) ให้คำแนะนำได้ไม่เท่าโค้ชเก่า · ลูกค้าที่ใช้ CGM/นาฬิกาแล้วไม่เห็นว่าข้อมูลถูกใช้ จะเลิกส่ง

## 2. Goals

| # | เป้าหมาย | วัดยังไง |
|---|---|---|
| G1 | **ลูกค้า 1 คนได้ผลประเมินรวมทุกแหล่งหน้าเดียว** พร้อมบอกชัดว่าคำนวณจากอะไร ขาดอะไร เชื่อได้แค่ไหน | ทุกลูกค้าที่มีข้อมูล ≥1 แหล่ง มี Health Design Assessment ที่ระบุ `sources_used[]` · `data_gaps[]` · `confidence` |
| G2 | **ทุกข้อมูลที่ลูกค้าส่งมาถูกใช้** — ไม่มีแหล่งไหนเข้าระบบแล้วจบอยู่ที่ตารางเดียว | CGM · food · wearable ปรากฏใน assessment ภายใน 1 ชั่วโมงหลังข้อมูลมาถึง |
| G3 | **แผนดูแลเฉพาะบุคคลออกจากผลประเมิน ไม่ใช่จากความจำโค้ช** — โค้ชเป็นคน**ยืนยัน/แก้** ไม่ใช่คนเขียนจากศูนย์ | ≥80% ของแผนที่ส่งลูกค้าเริ่มจากร่างที่ระบบสร้าง (นับจาก `plan.origin`) |
| G4 | **ลูกค้าใหม่เห็นผลประเมินแรกได้เองภายใน 10 นาที** นับจากได้ลิงก์ (มีแล็บหรือ BCA 1 ชุด) โดยโค้ชไม่ต้องแตะ | เวลาจาก `invite.created_at` → assessment แรก · เป้า median ≤10 นาที |
| G5 | **ใช้ผ่าน AI ตัวไหนก็ได้เท่ากับใช้ผ่านแอป** — ทุกความสามารถของ §3 มี tool ใน MCP | tool ใน `/api/mcp` ครอบ 100% ของ capability ใน §3 (ตรวจด้วย test) |

## 3. What we build — แยกเป็น 6 ชิ้น

### 3.1 Assessment Engine — ประเมินรวม 5 แหล่ง (P0)

หนึ่ง object ต่อลูกค้าต่อครั้ง: `health_assessments`

```
{
  customer_id, computed_at, trigger: "lab_import" | "cgm_import" | "food_log" | "wearable_sync" | "manual",
  sources_used: ["labs","bca","cgm","wearable","food"],        // เฉพาะที่มีข้อมูลจริงในหน้าต่างเวลา
  data_gaps: [{ source:"wearable", reason:"ไม่เคยเชื่อม" }, { source:"labs", reason:"hs-CRP ไม่มี → PhenoAge ประมาณ" }],
  confidence: "high" | "medium" | "low",                         // กฎใน lib/ ไม่ใช่ LLM
  domains: {
    metabolic:   { level: good|watch|attention|null, drivers:[{metric,value,level,source}], caveats[] },  // ไม่มี score   // HbA1c · FBS · CGM TIR/CV/GMI · food glycemic load
    body_comp:   { … },   // BCA fat% · visceral · muscle · body-age
    cardio_lipid:{ … },   // LDL/HDL/TG · resting HR · HRV (wearable)
    liver_kidney:{ … },   // ALT/AST/eGFR · uric
    recovery:    { … },   // sleep · HRV · strain (wearable) — null ถ้าไม่มี
    nutrition:   { … },   // โปรตีน/วัน vs เป้า · C:P:F · ความถี่บันทึก — null ถ้าไม่มี
    health_age:  { phenoage, delta, mode:"measured"|"hybrid" }
  },
  priorities: [ { rank, domain, why, evidence:[…] } ],           // 3 อันดับที่ควรทำก่อน
  disclaimer
}
```

**กฎที่ล็อกไว้**
- ตรรกะทั้งหมดใน `lib/health-design/assess.ts` (pure · มี test) — หน้าเว็บ/API/MCP เรียกตัวเดียวกัน (AGENTS.md ข้อ 1.2)
- **ไม่มีข้อมูล ≠ ปกติ** — domain ที่ไม่มีข้อมูลเป็น `null` + อยู่ใน `data_gaps` ห้ามให้คะแนนกลาง ๆ
- คะแนนย่อยที่มีอยู่แล้ว (Health Score · `insight-rules.ts` · `status-classifier.ts` · CGM `computeMetrics` · PhenoAge) **ถูกเรียกใช้ ไม่เขียนใหม่**
- CGM เข้าเงื่อนไข "เชื่อได้" เมื่อ ≥14 วัน + ≥70% (Battelino 2019) · ต่ำกว่านั้นใช้เป็นแนวโน้ม ห้ามเทียบเกณฑ์ (มีอยู่แล้วใน `cgm-metrics.ts`)
- **wellness ≠ diagnosis** — `priorities.why` ห้ามใช้คำว่าโรค ใช้ "ค่า X อยู่ในช่วงที่ควรปรึกษาแพทย์"

**Acceptance**
- [x] ลูกค้าที่มีแค่แล็บ 1 ใบ → assessment มี `metabolic`, `cardio_lipid`, `liver_kidney`, `health_age` และ `data_gaps` ระบุ bca/cgm/wearable/food
- [x] นำเข้า CGM 14 วันครบ → `metabolic.drivers` มี TIR/CV/GMI พร้อม `source:"cgm"` และ `confidence` ขยับขึ้น
- [x] ค่า LDL 190 → `priorities[0].domain = cardio_lipid` และ `why` ไม่มีคำว่า "โรค"/"วินิจฉัย"
- [x] assessment เดิมไม่ถูกลบเมื่อคำนวณใหม่ (เก็บประวัติ เทียบย้อนหลังได้)

### 3.4 ฐานอ้างอิง — สิ่งที่ทำให้ "เทียบกับข้อมูลใหญ่" เป็นความจริง (P1)

ข้อมูลของเรา 104 คน ไม่ใช่ big data · สิ่งที่ลูกค้าได้ประโยชน์จริงคือ **เทียบตัวเองกับประชากรและเกณฑ์สากล**:

| ชั้น | แหล่ง | ใช้ทำอะไร |
|---|---|---|
| เกณฑ์คลินิก | ADA · ESC/EAS lipid · KDIGO · Battelino 2019 (CGM) · Levine 2018 (PhenoAge) — มีใน `lib/` แล้วบางส่วน | สถานะ ปกติ/ก้ำกึ่ง/ควรพบแพทย์ |
| เปอร์เซ็นไทล์ประชากร | **ต้องเลือก** — NHANES (สหรัฐ · เปิด) · Thai NHES (ไทย · ต้องขอ) | "คุณอยู่ตรงไหนเมื่อเทียบคนอายุ/เพศเดียวกัน" |
| กลุ่มของเรา | ลูกค้า UP Wellness (ไม่ระบุตัวตน · ต้องมี consent) | "คนที่เริ่มเหมือนคุณ 90 วันถัดมาเป็นยังไง" — ทำได้เมื่อ n พอ (§7 Q1) |

**คำโปรโมตที่พูดได้ตั้งแต่วันนี้:** "เทียบผลของคุณกับเกณฑ์สากลและฐานประชากร" — ไม่ใช่ "เรามีข้อมูลขนาดใหญ่"

### 3.5 "Realtime" = ประเมินใหม่ทันทีที่ข้อมูลมาถึง (P1)

- ทุกการเขียน labs / measurements / cgm_readings / food_entries / pulse_readings → trigger `assess()` ใหม่ (queue ไม่ใช่ sync ในคำขอ) → assessment ใหม่ภายใน ≤60 วินาที
- ทำให้ข้อมูลมาถึงถี่ขึ้น: Ottai ยังเป็นไฟล์ export (ไม่พบ public API — §7 Q3) · Whoop OAuth ดึงรายวันได้แล้ว · Apple Health ต้องอัปโหลด
- **คำที่พูดได้:** "ผลประเมินอัปเดตทันทีที่ข้อมูลใหม่เข้ามา" · **คำที่ยังพูดไม่ได้:** "ดูน้ำตาลสด ๆ นาทีต่อนาที"

### 3.6 หน้าลูกค้า self-serve (P1) + ใช้ผ่าน AI ของตัวเอง (P0 — มีแล้ว ขยาย)

- ลูกค้าเข้าด้วยลิงก์ token (แบบ `/connect`, `/r` ที่มีอยู่) หรือ LINE → เห็น assessment ล่าสุด · แผน · ส่งอาหาร/รูป · อัปโหลดไฟล์ CGM เอง
- ✅ `/my/<token>`: ประเมิน · แผน · บันทึกอาหาร (AI ด้วยคีย์ระบบ จำกัด 40/วัน) · อัปโหลด CGM · โค้ชสร้าง/หมุนลิงก์จากการ์ดผลประเมิน
- ลูกค้าที่อยากใช้ AI ตัวเอง: ต่อ `/api/mcp` ด้วย OAuth (มีแล้ว) — **ต้องเพิ่ม role ลูกค้า** ที่เห็นเฉพาะตัวเอง (วันนี้ OAuth รับเฉพาะบัญชีโค้ช/แอดมิน — §7 Q5 ยังค้าง)

## 5. Success Metrics

ยังไม่มี baseline สักตัว — **สัปดาห์แรกหลังปล่อยคือการวัด baseline** ไม่ใช่การตัดสิน

| ตัวชี้วัด | นิยาม | เป้า (90 วันหลังปล่อย) | วัดจาก |
|---|---|---|---|
| Time-to-first-assessment | invite → assessment แรก | median ≤10 นาที | `user_invites.created_at` vs `health_assessments.computed_at` |
| Source coverage | % ลูกค้า active ที่มี ≥3 แหล่งใน 30 วัน | ≥40% | `sources_used` |
| Food log retention | % ลูกค้าที่บันทึกอาหาร ≥4 วัน/สัปดาห์ ต่อเนื่อง 4 สัปดาห์ | ≥30% | `food_entries` |
| Plan origin | % แผนที่เริ่มจาก engine | ≥80% | `health_plans.origin` |
| Coach edit distance | โค้ชแก้กี่ % ของร่าง | ลดลงทุกเดือน | diff ที่เก็บ |
| AI channel share | % การอ่าน assessment ผ่าน MCP vs แอป | รายงานอย่างเดียว ไม่ตั้งเป้า | `api_token_logs.user_agent LIKE 'mcp:%'` |

## 6. Non-Goals (v1)

1. **ไม่วินิจฉัยและไม่แนะนำยา** — ค่าเกินเกณฑ์ = "ปรึกษาแพทย์" เท่านั้น
2. **ไม่ให้ระบบเสนออาหารเสริมเอง** — เภสัชกรจัด ระบบแค่แสดง (กฎเดิม PRD §6)
3. **ไม่ทำ streaming CGM นาทีต่อนาที** — ไม่มีแหล่งข้อมูลที่ให้ได้ (Ottai = ไฟล์)
4. **ไม่ทำแอป native** — เว็บ + LINE + MCP พอสำหรับ "ใช้ผ่านแอป" ในความหมายลูกค้า
5. **ไม่เทรนโมเดลของเราเอง** จากข้อมูล 104 คน — ใช้กฎ + เกณฑ์ + LLM ที่ผู้ใช้ถือคีย์เอง (BYO) ตามเดิม
6. **ไม่เปิดข้อมูลรวมของลูกค้า (cohort)** จนกว่ามี consent เฉพาะและ n ที่ไม่ระบุตัวตนได้
