0คำสัญญาที่จะใช้โปรโมต — และสิ่งที่ต้องเป็นจริงก่อนพูด

ต้นอยากพูดกับลูกค้าว่า:

"เข้ามาอยู่กับเรา มีระบบประเมินและออกแบบการดูแลสุขภาพเฉพาะบุคคล บนฐานข้อมูลขนาดใหญ่ ออกแบบ lifestyle อาหารการกิน ประเมินได้แบบ realtime ใช้ผ่านแอปก็ได้ หรือผ่าน AI ที่คุณถนัดก็ได้ ขั้นตอนไม่ยุ่งยาก"

แยกทีละคำว่า วันนี้จริงแค่ไหน (ตรวจจากโค้ดและฐานข้อมูล 12 ก.ย. 2026):

คำในโปรโมตวันนี้ต้องทำอะไรถึงพูดได้เต็มปาก
"ประเมินสุขภาพจากแล็บ"✅ จริง — customer_lab_values + เกณฑ์ lib/medical-status.ts + PhenoAge + คิวตรวจใบแล็บที่ AI อ่าน—
"จาก BCA"✅ จริง — measurements + Health Score (BCA 40% · Lab 40% · Recency 20%)—
"จาก CGM"✅ จริง — cgm_readings >50,000 ค่า · TIR/CV/GMI ตามเกณฑ์สากล · นำเข้าไฟล์ Ottai ผ่าน APIยังไม่รวมเข้า Health Score (§3.1)
"จาก wearable"⚠️ ครึ่งเดียว — Whoop OAuth/CSV และ Apple Health export ใช้ได้ · Google Fit ตาย (PRD §12)ทางเดินใหม่สำหรับ Android (§7 Q3)
"จากอาหารที่บันทึก"⚠️ แยกส่วน — NutriScan (รูป→มาโคร) และ Food Log มี แต่ไม่มี "พิมพ์เอง" · ไม่มี "เอารูปเก่ามาลงย้อนหลัง" · ไม่ป้อนเข้าการประเมิน§3.2
"ฐานข้อมูลขนาดใหญ่"❌ ยังพูดไม่ได้ — ลูกค้าในระบบ 104 คน · ข้อมูลของเราไม่ใช่ "ขนาดใหญ่" · ถ้าจะพูด ต้องหมายถึง ฐานอ้างอิงประชากร + เกณฑ์สากล ที่ระบบเทียบให้ (§3.4)เลือกแหล่งอ้างอิงและเขียนคำโปรโมตให้ตรงความจริง (§7 Q1)
"ออกแบบ lifestyle / อาหาร"⚠️ มีชิ้นส่วน — Program Designer · Plate Planner (Muscle-Centric) · เมนู LINE 18:00 · ตารางอาหารเสริมยังไม่มี แผนเดียว ที่ถูกสร้างจากผลประเมินแล้วส่งถึงลูกค้า (§3.3)
"realtime"❌ ยังพูดไม่ได้ — ทุกแหล่งเป็น batch (อัปโหลดไฟล์/ sync เป็นรอบ)นิยามใหม่เป็น "ประเมินใหม่ทันทีที่ข้อมูลใหม่มาถึง" และทำให้ข้อมูลมาถึงถี่ขึ้น (§3.5)
"ผ่านแอป"⚠️ แอปวันนี้เป็นของโค้ช — ลูกค้าได้แค่ลิงก์ token (/connect, /intake, /r) และ LINEหน้าลูกค้าแบบ self-serve (§3.6)
"ผ่าน AI ที่คุณถนัด"✅ จริงแล้ววันนี้ — MCP /api/mcp + OAuth · claude.ai / ChatGPT / Claude Code / Cursor / Gemini CLI ต่อได้ · เอกสารฉบับนี้ถูกเขียนโดย Claude ที่อ่านข้อมูลผ่าน connector OAuth · Claudeขยาย tool ให้ครอบ food/wearable/plan (§4)
"ขั้นตอนไม่ยุ่งยาก"⚠️ วัดไม่ได้ — ยังไม่เคยนับว่าลูกค้าใหม่ 1 คนใช้กี่ขั้น/กี่นาทีกว่าจะเห็นผลประเมินแรกนิยาม + วัด (§5)

สรุป: 4 ใน 9 คำพูดได้วันนี้ · 3 คำพูดได้ครึ่งเดียว · 2 คำ ("ฐานข้อมูลขนาดใหญ่", "realtime") ยังพูดไม่ได้ และเป็นความเสี่ยงโฆษณาเกินจริงถ้าพูดก่อนทำ

1Problem Statement

โค้ช UP Wellness มีข้อมูลลูกค้า 5 แหล่งอยู่ในระบบแล้ว (แล็บ · BCA · CGM · นาฬิกา · อาหาร) แต่ระบบประเมินแยกกัน: Health Score ดูแค่แล็บ+BCA · CGM มีตัวเลขสรุปแต่ไม่ถูกนำไปรวม · อาหารกับนาฬิกาอยู่คนละหน้า → โค้ชยังต้อง "รวมในหัว" แล้วเขียนแผนเอง ผลคือแผนไม่สม่ำเสมอระหว่างโค้ช พิสูจน์ที่มาไม่ได้ และลูกค้าเห็นผลก็ต่อเมื่อโค้ชว่างมาสรุปให้

ผลกระทบถ้าไม่แก้: คำโปรโมต "ออกแบบเฉพาะบุคคลบนข้อมูล" จะเป็นคำที่ทีมขายพูดแต่ระบบทำไม่ได้ · โค้ชใหม่ (downline) ให้คำแนะนำได้ไม่เท่าโค้ชเก่า · ลูกค้าที่ใช้ CGM/นาฬิกาแล้วไม่เห็นว่าข้อมูลถูกใช้ จะเลิกส่ง

2Goals

#เป้าหมายวัดยังไง
G1ลูกค้า 1 คนได้ผลประเมินรวมทุกแหล่งหน้าเดียว พร้อมบอกชัดว่าคำนวณจากอะไร ขาดอะไร เชื่อได้แค่ไหนทุกลูกค้าที่มีข้อมูล ≥1 แหล่ง มี Health Design Assessment ที่ระบุ sources_used[] · data_gaps[] · confidence
G2ทุกข้อมูลที่ลูกค้าส่งมาถูกใช้ — ไม่มีแหล่งไหนเข้าระบบแล้วจบอยู่ที่ตารางเดียวCGM · food · wearable ปรากฏใน assessment ภายใน 1 ชั่วโมงหลังข้อมูลมาถึง
G3แผนดูแลเฉพาะบุคคลออกจากผลประเมิน ไม่ใช่จากความจำโค้ช — โค้ชเป็นคนยืนยัน/แก้ ไม่ใช่คนเขียนจากศูนย์≥80% ของแผนที่ส่งลูกค้าเริ่มจากร่างที่ระบบสร้าง (นับจาก plan.origin)
G4ลูกค้าใหม่เห็นผลประเมินแรกได้เองภายใน 10 นาที นับจากได้ลิงก์ (มีแล็บหรือ BCA 1 ชุด) โดยโค้ชไม่ต้องแตะเวลาจาก invite.created_at → assessment แรก · เป้า median ≤10 นาที
G5ใช้ผ่าน AI ตัวไหนก็ได้เท่ากับใช้ผ่านแอป — ทุกความสามารถของ §3 มี tool ใน MCPtool ใน /api/mcp ครอบ 100% ของ capability ใน §3 (ตรวจด้วย test)

3What we build — แยกเป็น 6 ชิ้น

3.1 Assessment Engine — ประเมินรวม 5 แหล่ง (P0)

หนึ่ง object ต่อลูกค้าต่อครั้ง: health_assessments

{
  customer_id, computed_at, trigger: "lab_import" | "cgm_import" | "food_log" | "wearable_sync" | "manual",
  sources_used: ["labs","bca","cgm","wearable","food"],        // เฉพาะที่มีข้อมูลจริงในหน้าต่างเวลา
  data_gaps: [{ source:"wearable", reason:"ไม่เคยเชื่อม" }, { source:"labs", reason:"hs-CRP ไม่มี → PhenoAge ประมาณ" }],
  confidence: "high" | "medium" | "low",                         // กฎใน lib/ ไม่ใช่ LLM
  domains: {
    metabolic:   { level: good|watch|attention|null, drivers:[{metric,value,level,source}], caveats[] },  // ไม่มี score   // HbA1c · FBS · CGM TIR/CV/GMI · food glycemic load
    body_comp:   { … },   // BCA fat% · visceral · muscle · body-age
    cardio_lipid:{ … },   // LDL/HDL/TG · resting HR · HRV (wearable)
    liver_kidney:{ … },   // ALT/AST/eGFR · uric
    recovery:    { … },   // sleep · HRV · strain (wearable) — null ถ้าไม่มี
    nutrition:   { … },   // โปรตีน/วัน vs เป้า · C:P:F · ความถี่บันทึก — null ถ้าไม่มี
    health_age:  { phenoage, delta, mode:"measured"|"hybrid" }
  },
  priorities: [ { rank, domain, why, evidence:[…] } ],           // 3 อันดับที่ควรทำก่อน
  disclaimer
}

กฎที่ล็อกไว้

  • ตรรกะทั้งหมดใน lib/health-design/assess.ts (pure · มี test) — หน้าเว็บ/API/MCP เรียกตัวเดียวกัน (AGENTS.md ข้อ 1.2)
  • ไม่มีข้อมูล ≠ ปกติ — domain ที่ไม่มีข้อมูลเป็น null + อยู่ใน data_gaps ห้ามให้คะแนนกลาง ๆ
  • คะแนนย่อยที่มีอยู่แล้ว (Health Score · insight-rules.ts · status-classifier.ts · CGM computeMetrics · PhenoAge) ถูกเรียกใช้ ไม่เขียนใหม่
  • CGM เข้าเงื่อนไข "เชื่อได้" เมื่อ ≥14 วัน + ≥70% (Battelino 2019) · ต่ำกว่านั้นใช้เป็นแนวโน้ม ห้ามเทียบเกณฑ์ (มีอยู่แล้วใน cgm-metrics.ts)
  • wellness ≠ diagnosis — priorities.why ห้ามใช้คำว่าโรค ใช้ "ค่า X อยู่ในช่วงที่ควรปรึกษาแพทย์"

3.4 ฐานอ้างอิง — สิ่งที่ทำให้ "เทียบกับข้อมูลใหญ่" เป็นความจริง (P1)

ข้อมูลของเรา 104 คน ไม่ใช่ big data · สิ่งที่ลูกค้าได้ประโยชน์จริงคือ เทียบตัวเองกับประชากรและเกณฑ์สากล:

ชั้นแหล่งใช้ทำอะไร
เกณฑ์คลินิกADA · ESC/EAS lipid · KDIGO · Battelino 2019 (CGM) · Levine 2018 (PhenoAge) — มีใน lib/ แล้วบางส่วนสถานะ ปกติ/ก้ำกึ่ง/ควรพบแพทย์
เปอร์เซ็นไทล์ประชากรต้องเลือก — NHANES (สหรัฐ · เปิด) · Thai NHES (ไทย · ต้องขอ)"คุณอยู่ตรงไหนเมื่อเทียบคนอายุ/เพศเดียวกัน"
กลุ่มของเราลูกค้า UP Wellness (ไม่ระบุตัวตน · ต้องมี consent)"คนที่เริ่มเหมือนคุณ 90 วันถัดมาเป็นยังไง" — ทำได้เมื่อ n พอ (§7 Q1)

คำโปรโมตที่พูดได้ตั้งแต่วันนี้: "เทียบผลของคุณกับเกณฑ์สากลและฐานประชากร" — ไม่ใช่ "เรามีข้อมูลขนาดใหญ่"

3.5 "Realtime" = ประเมินใหม่ทันทีที่ข้อมูลมาถึง (P1)

  • ทุกการเขียน labs / measurements / cgm_readings / food_entries / pulse_readings → trigger assess() ใหม่ (queue ไม่ใช่ sync ในคำขอ) → assessment ใหม่ภายใน ≤60 วินาที
  • ทำให้ข้อมูลมาถึงถี่ขึ้น: Ottai ยังเป็นไฟล์ export (ไม่พบ public API — §7 Q3) · Whoop OAuth ดึงรายวันได้แล้ว · Apple Health ต้องอัปโหลด
  • คำที่พูดได้: "ผลประเมินอัปเดตทันทีที่ข้อมูลใหม่เข้ามา" · คำที่ยังพูดไม่ได้: "ดูน้ำตาลสด ๆ นาทีต่อนาที"

3.6 หน้าลูกค้า self-serve (P1) + ใช้ผ่าน AI ของตัวเอง (P0 — มีแล้ว ขยาย)

  • ลูกค้าเข้าด้วยลิงก์ token (แบบ /connect, /r ที่มีอยู่) หรือ LINE → เห็น assessment ล่าสุด · แผน · ส่งอาหาร/รูป · อัปโหลดไฟล์ CGM เอง
  • ✅ /my/<token>: ประเมิน · แผน · บันทึกอาหาร (AI ด้วยคีย์ระบบ จำกัด 40/วัน) · อัปโหลด CGM · โค้ชสร้าง/หมุนลิงก์จากการ์ดผลประเมิน
  • ลูกค้าที่อยากใช้ AI ตัวเอง: ต่อ /api/mcp ด้วย OAuth (มีแล้ว) — ต้องเพิ่ม role ลูกค้า ที่เห็นเฉพาะตัวเอง (วันนี้ OAuth รับเฉพาะบัญชีโค้ช/แอดมิน — §7 Q5 ยังค้าง)

6Non-Goals (v1)

  1. ไม่วินิจฉัยและไม่แนะนำยา — ค่าเกินเกณฑ์ = "ปรึกษาแพทย์" เท่านั้น
  2. ไม่ให้ระบบเสนออาหารเสริมเอง — เภสัชกรจัด ระบบแค่แสดง (กฎเดิม PRD §6)
  3. ไม่ทำ streaming CGM นาทีต่อนาที — ไม่มีแหล่งข้อมูลที่ให้ได้ (Ottai = ไฟล์)
  4. ไม่ทำแอป native — เว็บ + LINE + MCP พอสำหรับ "ใช้ผ่านแอป" ในความหมายลูกค้า
  5. ไม่เทรนโมเดลของเราเอง จากข้อมูล 104 คน — ใช้กฎ + เกณฑ์ + LLM ที่ผู้ใช้ถือคีย์เอง (BYO) ตามเดิม
  6. ไม่เปิดข้อมูลรวมของลูกค้า (cohort) จนกว่ามี consent เฉพาะและ n ที่ไม่ระบุตัวตนได้

7Open Questions

#คำถามใครตอบบล็อกไหม
Q1⚠️ ทำบนสมมติฐาน NHANES (สหรัฐ) ไปก่อน ติดป้ายทุกจุด — ยังต้องเคาะว่าจะขอ Thai NHES ไหม · ฐานเปอร์เซ็นไทล์ประชากรใช้อะไร — NHANES (ได้เลย แต่เป็นคนอเมริกัน) หรือขอ Thai NHES (ตรงกว่า ใช้เวลา) · และคำโปรโมต "ฐานข้อมูลขนาดใหญ่" จะเปลี่ยนเป็นคำไหนต้น + จิ้นบล็อก §3.4 และการตลาด
Q2PDPA: อาหาร/รูปอาหาร/ข้อมูลนาฬิกาเป็นข้อมูลอ่อนไหวมาตรา 26 — consent ปัจจุบัน (/intake, /connect) ครอบการเก็บรูปและการเทียบ cohort ไหมต้น (+ ที่ปรึกษากฎหมาย)บล็อก §3.2 / §3.4
Q3Android wearable: Google Fit ตายสิ้นปี — Health Connect (ต้องมีแอป native) หรือให้อัปโหลดไฟล์ · และ Ottai มี API จริงไหม (ยังไม่พบเอกสารสาธารณะ)วิศวกรรม (ผม spike 2 วัน)ไม่บล็อก — v1 ใช้ไฟล์
Q4Food log ทาง LINE: พอร์ต meal-tracker จาก UP Line เข้า uplabs หรือให้ UP Line เขียนเข้า uplabs ผ่าน logFoodต้นไม่บล็อก — เริ่มจากหน้าเว็บ + MCP ก่อน
Q5⚠️ ทำบนสมมติฐาน token link (/my/<token>) ไม่มีบัญชี — ลูกค้าต่อ AI ของตัวเองผ่าน OAuth ยังไม่ได้ · ลูกค้าจะมีบัญชีล็อกอินเองไหม (จำเป็นถ้าจะให้ลูกค้าต่อ AI ของตัวเองผ่าน OAuth) หรือใช้ลิงก์ token อย่างเดียวต้นบล็อก §3.6 ครึ่งหลัง
